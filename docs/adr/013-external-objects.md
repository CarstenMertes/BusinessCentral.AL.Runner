# ADR-013: Objects outside the workspace (platform objects)

- Status: Proposed
- Date: 2026-10-13

## Context

The corpus references Microsoft System Application and Base Application
objects whose source is not in the workspace (the corpus manifest lists
System Application, Base Application, System Application Test Library and
Permissions Mock as dependencies). Today the runtime treats every such
reference the same way:

- `al-sema/src/workspace.rs` (`resolve_references`) reports
  `AR0002 unresolved <kind> '<name>'` for every type reference that does not
  resolve. `crates/al-sema/tests/expected-unresolved.txt` is the golden list of
  them: 202 distinct objects, 1062 references (table 112 objects / 736
  references, page 43 / 102, report 18 / 68, codeunit 12 / 81, enum 11 / 58,
  xmlport 4 / 12, query 2 / 5). `corpus_resolve.rs` fails if the list changes,
  so it is already the backlog of this ADR.
- `al-sema/src/check.rs` does not guess: a record of an unresolved table has
  `Ty::Unknown` fields (`field_of`), a call on an unknown callee is not
  checked.
- `al-sema/src/lower.rs` (`resolve_obj`, `rt`) refuses to lower a variable of
  an unresolved type, so the test is reported not run with
  `` `Var`: <kind> `X` is outside the workspace``. Extensions of an external
  table are accepted but have no base to merge into.

That is hard rule 4 working as designed. This ADR asks whether, and how, to do
better.

where it ends. That affects priority (open question 8), not the design.

### Constraints

- Hard rule 4: an unimplemented thing is a compile-time diagnostic that names
  it, never a runtime surprise.
- Hard rule 3: semantics come from the corpus or a probe, not from memory.
  Platform behaviour we do not have a pin for is not implemented.
- ADR-009: whatever AL can observe of a platform object must match BC: object
  id and name (`Codeunit::"Temp Blob"`, `Database::Customer`), members and
  their errors, schema (field numbers, `RecordRef` enumeration), triggers and
  events fired, instance semantics of codeunits (single instance, `var`
  parameters, `Clear`), what `AllObj` says. Internals are free.
- ADR-006: no OS access in core crates. Reading `.app` files or bundled
  directories happens in the CLI/host; sema receives `AppSource` values.
- Licensing (project owner): we must not copy Microsoft source. Whatever is
  bundled is written by us from corpus evidence, probes and facts (ids, names,
  field numbers, signatures), never transcribed.
- ADR-001/003/005/010/011: the IR, Store, Ctx and Value seams change only
  through an ADR. A solution that needs none of them is preferred.

## Options

### (a) Native implementations in Rust, registered by object name and member

Like builtins (ADR-008): a table keyed by `Codeunit."Temp Blob".CreateOutStream`
with a Rust function, plus a signature catalog the checker reads.

- Observable-equivalence risk: low for pure functions (`Base64 Convert`,
  `Environment Information`), high for anything stateful or record-backed.
  A native `Temp Blob` has to reproduce codeunit instance semantics by hand
  (by-`var` passing through interface dispatch, `Clear` not detaching the
  caller's instance, single-instance): exactly the behaviours
  `TestInterfaceVarCodeunitOut.al` exists to pin and which the VM already has
  for AL codeunits. Platform objects that publish integration events or have
  triggers would have to raise them by hand, in the right order.
- Effort: every member is Rust plus a hand-written signature entry. There is
  no `al-surface.json` for platform objects (the scrape covers language types
  only), so a second catalog format and its generation process is needed.
  Tables are the worst case: a table needs fields, keys, triggers, relations
  and the whole record machinery, which is what AL declarations give for free.
- Refusal: natural. A member without a registered function is refused at
  lower time as an unimplemented builtin is ("builtin X is not implemented").
- Seams: `Value::Codeunit(Instance)` is tied to an object index; a native
  object needs a new `Value` variant (ADR-010) or a synthetic object;
  ADR-008's catalog is keyed by receiver type, not by object, so it needs an
  amendment; `Ctx` grows whenever a native member needs the store or events.

### (b) Bundled AL shim source for selected platform objects

Platform apps written by us as `.al` text, compiled into the workspace as
extra apps with the real App ids (the corpus manifest already names them, so
`visible_from` makes them visible with no new rule), real object ids, names
and namespaces. Behaviour is whatever our AL says, pinned by corpus evidence.

- Observable-equivalence risk: medium and, importantly, local to the member.
  Instance semantics, `var` passing, events, triggers, temporary-table
  isolation, error texts and Store behaviour are the ones every other AL object
  gets, so the entire class of "does the native object behave like a codeunit"
  bugs disappears. What remains is fidelity to BC for what the shim does:
  unpinned triggers (a Base App table's `OnInsert` is real logic), error
  texts, the schema (a table with only the fields the corpus touches is
  observably smaller than BC's: `RecordRef.FieldCount`, `TransferFields`,
  `Field` rows). The schema problem is the one real hazard; see
  "Partial tables".
- Effort: lowest per object, and it exercises the runtime (every shim member is
  a test of the language features we claim to support). Hand-written text, so
  the discipline is evidence: nothing is declared that the corpus or a probe
  does not pin.
- Refusal: an undeclared member is already `AR1002 no member` at check
  time, but the message does not say "this is a platform object and we only
  implement some of it". Needs a better diagnostic, nothing structural.
- Seams: none. Platform apps are ordinary `AppSource`s; they flow through
  parse, resolve, check, lower, link; tables use the Store, temporary
  variables get private stores, events and triggers use the existing
  dispatch. The only new thing is that the CLI adds them to the app list.
- Weakness: cannot express what AL cannot (generated rows, program metadata,
  host answers, base64, hashing, ...), and a shim table that is "hidden"
  (a helper for `Temp Blob`) must not appear in `AllObj`.

### (c) Load symbols (or source) from Microsoft `.app` packages

An `.app` is a zip with a manifest, `SymbolReference.json` (every object, its
fields with ids and types, procedures and signatures, enum values, event
publishers) and compiled code. Source may be shipped inside some packages.

- Observable-equivalence risk: zero for the surface (ids, names, schema, enum
  ordinals, signatures are exactly BC's) and unbounded for behaviour, because
  symbols contain none. The compiled code is IL for the BC server, useless to
  us. If a package happens to carry AL source, using it is the copying the
  project forbids; the loader must read `SymbolReference.json` only.
- Effort: zip and JSON loader, a "declaration-only object" path in sema
  (objects with members and no bodies), enum values, table schemas, event
  publishers. Version-sensitive (27.5 vs 28.1). Base App symbols are tens of
  thousands of objects, which collides with the 1 s cold-compile budget unless
  loading is lazy by reference.
- Provenance: the packages cannot be committed or redistributed by us; the
  user or CI must supply them (BC artifacts), so every run needs an input the
  repository does not contain, which breaks "`cargo test` is self-contained".
- Refusal: strong. A declared-only member that has no implementation is
  refused at lower time with "exists in BC 27.5, not implemented", the best
  diagnostic of the four options.
- Seams: new input type to sema, loaded in the CLI (ADR-006). IR, Store, Ctx
  unchanged. It does not run anything by itself, so it always needs (a) or
  (b) behind it.

### (d) Keep refusing

- Risk: none. Effort: none. The 516 tests stay not run, the ratchet does not
  grow from this class, and no platform behaviour is ever guessed.
- It matches the spike scope ("Tier 1: no Base App", `docs/handoff.md`) and the
  handoff question "go on to Base App type-checking?" is then answered by not
  asking it. The cost is that `TestInterfaceVarCodeunitOut` and similar tests,
  which pin core language behaviour and merely use `Temp Blob` as a vehicle,
  stay dark, and that other agents keep hitting the same wall.
- Refusal: already explicit, but the message is "outside the workspace", which
  cannot distinguish "we chose not to" from "does not exist".
- Seams: none.

### Comparison

| | (a) native | (b) AL shim | (c) symbols | (d) refuse |
|---|---|---|---|---|
| Surface fidelity (ids, schema) | by hand | by hand, evidence-pinned | exact | n/a |
| Behaviour fidelity | by hand in Rust, instance semantics re-done | AL semantics for free, content by hand | none | n/a |
| Effort per object | high | low | per-package fixed cost, then ~0 | none |
| Needs data outside the repo | no | no | yes | no |
| Hard rule 4 | per member, like builtins | no-member diagnostic, improved message | per member, best message | present message |
| Seam changes | Value, catalog, Ctx | none | sema input | none |
| Can do generated rows / metadata / host | yes | no | no | no |

## Decision (proposed)

Build (b) as the mechanism, use (a) only behind it for members AL cannot
express, use (c) only as a verifier, keep (d) for everything not yet pinned.

1. **Platform apps.** A new crate `al-platform` (pure, no OS access) embeds
   `.al` files under `platform/<app>/` with `include_str!` and returns
   `Vec<AppSource>`: System Application and Base Application, with the ids
   already in the corpus manifest, so dependency resolution is unchanged. The
   CLI appends them before the corpus apps. Each object keeps its real id,
   name, namespace and, for tables, real field numbers and types. Object ids
   and field numbers are facts and are pinned by probe where the corpus does
   not show them (hard rule 3); they are not taken from memory.
2. **Native-backed members.** A procedure in a platform app may be declared
   with an attribute `[PlatformNative('<id>')]` and no body. Lowering resolves
   the id in the same registry as ADR-008 (a second id namespace,
   `Platform.<Object>.<Member>`); the function receives `&mut dyn Ctx` as every
   builtin does. An id without a registered function is a compile diagnostic
   (`AR1101 platform member X is not implemented`). The attribute is rejected
   in any app that is not a platform app. This is the escape hatch for
   `Base64 Convert`, host answers and hashing; it adds no `Value` variant,
   because the object around it is still an ordinary AL codeunit.
3. **Refusal stays explicit (hard rule 4).** Three levels, all compile-time:
   - an undeclared member of a platform object: `AR1002` with a text that says
     the object is a platform object and lists the members the runtime
     implements (so "does not exist in BC" and "not implemented here" are
     distinguishable once item 6 exists);
   - a declared member whose behaviour is not pinned can be written as
     `[PlatformUnsupported('reason')]` with no body: a call is `AR1100`;
   - a native id with no function: `AR1101`.
   A platform object is never "mostly working": a call either resolves to
   pinned behaviour or the test codeunit does not compile.
4. **Evidence discipline.** Every platform member carries a comment
   `// pinned by: <corpus path>:<procedure>` (or a probe name). A test in
   `al-platform` fails when a member has no pin or the pin does not exist in
   the corpus. Each file starts with a provenance line saying it was written
   from corpus evidence and public documentation, with no Microsoft source
   consulted. Review rejects text that looks transcribed.
5. **Hidden helpers.** Helper objects a shim needs (the table behind `Temp
   Blob`) take ids from a private range and are marked `[PlatformInternal]`;
   they do not appear in `AllObj`, `Database::` completion, `RecordRef.Open`
   by number, or the metadata tables (observable, ADR-009).
6. **Symbols as a verifier, not a dependency.** A test, skipped when no
   `.app` is available, compares each shim object's surface (id, name, field
   numbers and types, enum ordinals, procedure names and parameter lists)
   against `SymbolReference.json` and fails on any mismatch. Packages are read
   from a path in an environment variable and never committed. This catches
   hand-written errors with ground truth without making the runtime depend on
   Microsoft files. If the project owner approves, the same file is the source
   of the "exists in BC, not implemented" list for diagnostics.
7. **Out of scope here.** Class A and C tables (program metadata, `Date`,
   `Integer`) are generated, not written, and need a row provider behind the
   Store seam; that is an amendment to ADR-003 and gets its own ADR after the
   mechanism above has landed. Pages, reports and xmlports of the Base App
   stay refused. Business tables with real logic (`Customer`, `Item`) stay
   refused until partial tables are decided (open question 2).

### Partial tables

A shim table with only the fields the corpus touches differs from BC in
anything that enumerates the schema. If partial tables are accepted at all, a
table is declared `[PlatformPartial]` and any construct that observes the full
schema (`RecordRef.FieldCount`, `Field(i)`, `FieldIndex`, `KeyCount`,
`TransferFields` without an explicit field list, page or report auto-fields,
the `Field`/`Key` metadata tables) is `AR1102` for that table. The alternative is to require
exact schemas, which means (c) as an input and not a verifier. The first
increment contains no table, so this is a decision to take before the second.

## First increment

Scope: the mechanism and the smallest set of objects that proves each half
of it.

1. `al-platform` crate, loader, CLI wiring, and the improved diagnostics
   (items 1, 3, 5). No IR, Store, Ctx or Value change.
2. `Temp Blob` as AL (appendix A is the proof of feasibility): `CreateInStream`
   and `CreateOutStream`, each with the `TextEncoding` overload, and `Length`.
   Exactly the members the corpus calls; `HasValue`, `FromRecord`,
   `ToRecordRef` and the rest are refused until a pin exists. Needed
   generic fixes the measurement exposed (belong to the same branch, each with
   a red test first): `Clear` of a `var Codeunit` parameter, and
   `CreateOutStream(Out, TextEncoding::X)` on a codeunit receiver.
   Expected effect: `types/TestInterfaceVarCodeunitOut.al` (5 tests) passes,
   plus 1 to 2 tests more that other pending work already unblocks; 23 more
   tests then stop at their next blocker.
3. `Base64 Convert` (`ToBase64(InStream)`, `FromBase64(Text, OutStream)`) as
   the first `[PlatformNative]` members, to prove item 2 end to end. Two tests
   behind `Temp Blob` need it.
4. `Environment Information` as native-backed host answers (4 tests, all of
   them agreement checks), if the host-answer question (open question 4) is
   settled; otherwise it moves to the second increment.
5. The golden `expected-unresolved.txt` shrinks by the objects added, and is
   regenerated in the same commit (`UPDATE_GOLDEN=1`), so the list stays the
   backlog. The pass-rate gain is small by itself (about 5 tests); the
   value is the mechanism and the dark core tests.

Next candidates, by tests and by how well they fit: `Permissions Mock`,
`User Permissions`, `Reten. Pol. Allowed Tables`, `Application Area Mgmt.
Facade` (codeunits with few members each), then the generated tables
(`Date`, `Integer`: 33 tests) and program metadata (class A: 203 tests) under
a follow-up ADR, then permission tables and Base App business tables once
partial tables are decided.

## Consequences

- No seam moves: the IR, Store, Ctx and Value are untouched. ADR-008 gains a
  second registry id namespace; the sema input set gains platform apps. Both
  are small, and both are named here so review can object.
- The runtime ships Microsoft-compatible object ids and names authored by us.
  Anything that quotes BC text (error messages) is a pin from the corpus, not a
  copy.
- Every shim is a regression test for the language: a shim that cannot
  compile points at an unimplemented feature, which is where the 2 generic gaps
  measured above came from.
- Compile cost grows with the bundle; bundle size is part of the 1 s
  cold-compile budget and is covered by the perf test.
- `expected-unresolved.txt` becomes the visible platform backlog; its size is
  a metric next to catalog coverage.
- Risk: a plausible but wrong shim passes tests that do not look at the
  difference. The symbol verifier (item 6) and the pin rule (item 4) are the
  counter-measures, and both depend on corpus growth for coverage.

## Conformance

- `al-platform` tests: every platform file parses; every member has a `//
  pinned by:` comment whose target exists in the corpus; no
  `[PlatformInternal]` object is reachable from `AllObj`, `Database::` or
  `RecordRef.Open`.
- `al-sema` tests: `AR1002` text on a platform object names the implemented
  members; `[PlatformUnsupported]` call is `AR1100`; `[PlatformNative]` outside
  a platform app is rejected; an unknown native id is `AR1101`; a
  schema-observing construct on a `[PlatformPartial]` table is `AR1102`.
  (AR1003 and AR1004 are taken by the checker; AR11xx is the platform block.)
- `corpus_resolve.rs`: `expected-unresolved.txt` regenerated, shrinking only.
- A skipped-without-packages test comparing shim surfaces with
  `SymbolReference.json` (item 6).
- Corpus: `types/TestInterfaceVarCodeunitOut.al` and the other `Temp Blob`
  tests, via `metrics/passing.txt` (the ratchet, ADR-007).

## Open questions for the project owner

1. Licensing boundary. Does "do not copy Microsoft source" also cover
   Microsoft's open-source repositories, or is reading and vendoring them (with
   attribution, if their licence allows it; unverified here, this session had
   no access to check) acceptable? Is it acceptable to take names, ids and
   signatures from the public Learn reference, and to read `SymbolReference.json`
   from locally supplied `.app` files as a verifier that is never committed?
2. Partial tables: accept Base App tables with only the fields the corpus uses
   (with `[PlatformPartial]` refusing schema-observing constructs), or require
   exact schemas (which needs symbols as a real input), or refuse every Base
   App business table?
3. Is the "exists in BC but not implemented" distinction worth the symbols
   input in the first increment, or is the generic "platform object, only these
   members are implemented" message enough for now?
4. Environment and identity answers (`Environment Information`, `User Permissions`,
   `Session`, `Company`): what does the runtime claim to be (SaaS sandbox,
   on-premises), and may we probe the oracle container for it, since the tests
   only check that the answers agree with each other?
5. Delivery: platform apps embedded in the binary with `include_str!`
   (self-contained, reproducible) or read from a directory at run time?
6. A follow-up ADR for virtual system tables (generated `Date`/`Integer` and
   program metadata, about 250 tests), amending ADR-003 with a row provider:
   authorise now, or only after the first increment shows the mechanism works?
7. Base App pages, reports and xmlports (43 + 18 + 4 objects) stay refused
   here: confirm that ADR-012 and the report/xmlport work own them.
8. Priority. The measurement says a bundled `Temp Blob` passes 3 tests today and
   about 5 after two generic fixes; the other 23 wait for `Report.SaveAs`
   (9), `Media.ImportStream` (7), `Xmlport.Export/Import` (4). Is this the next
   thing to build, or should those builtins go first?
9. The `[PlatformNative]` / `[PlatformUnsupported]` / `[PlatformInternal]` /
   `[PlatformPartial]` attributes are a small sema surface recognised only in
   platform apps. Accept, or prefer a sidecar manifest per platform app?

## Appendix A: the measurement shim

Written for the measurement only, not committed as platform code. It uses
nothing but the three members the corpus calls.

```al
table 69990 "ZZ Shim TB Storage"
{
    TableType = Temporary;
    fields
    {
        field(1; "Code"; Code[10]) { }
        field(3; "Data"; Blob) { }
    }
    keys { key(PK; "Code") { Clustered = true; } }
}

codeunit 69991 "Temp Blob"
{
    var
        Storage: Record "ZZ Shim TB Storage" temporary;

    local procedure Ensure()
    begin
        if not Storage.Get('X') then begin
            Storage.Init();
            Storage.Code := 'X';
            Storage.Insert();
        end;
    end;

    procedure CreateInStream(var InStr: InStream)
    begin
        Ensure();
        Storage.CalcFields(Data);
        Storage.Data.CreateInStream(InStr);
    end;

    procedure CreateOutStream(var OutStr: OutStream)
    begin
        Ensure();
        Storage.Data.CreateOutStream(OutStr);
    end;

    procedure Length(): Integer
    begin
        Ensure();
        Storage.CalcFields(Data);
        exit(Storage.Data.Length());
    end;
}
```

The `TextEncoding` overloads and the pin comments are what the first
increment adds.
